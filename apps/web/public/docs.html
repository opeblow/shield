Shield API reference

Scan suspicious messages, verify official bank channels, read verified fraud reputation, and issue shareable check cards — from your app or banking platform.

Base URL https://your-shield-host · Spec openapi.yaml

Every endpoint returns a typed JSON object shown in each example below. Errors follow RFC 7807 problem+json.
Shield is versioned at /v1. Breaking changes arrive as a new version; /v1 is stable.

Authentication

Three authentication modes exist. Pick the one that matches your caller:

ModeHeader / cookieFor
Session cookieCookie: shield_session=…The Shield web app (register, sign in, certificates, reports).
Integration keyX-Api-Key: shd_live_…Banks, fintechs and servers calling /v1/integrations/*.
Moderator keyAuthorization: Bearer …Reviewing pending community reports.

Signed-in accounts can list active sessions at GET /v1/auth/sessions and revoke all other sessions with POST /v1/auth/sessions/revoke-others. Password reset and email verification are not available yet.

Integration keys

Create a key in the developer dashboard (signed in) or via the API. Keys carry scopes: scans:write, lookup:read, directory:read, certificates:read. The raw key is shown exactly once — store it on your server's secret manager.

curl https://your-shield-host/v1/integrations/scan \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: shd_live_…" \
  -d '{"text":"Please send your OTP to 0912 345 6789 now","language":"en"}'

Quickstart

Scan a message in your banking app before the transfer form is shown:

const response = await fetch("/v1/integrations/scan", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-Api-Key": "shd_live_…"
  },
  body: JSON.stringify({ text: "Send your OTP to 0912 345 6789" })
});
const result = await response.json();
// { verdict: "likely_scam", risk_score: 45, shield: { official_channels: […], reputation: […] } }

Gate the transfer on verdict, or pass the verdict into transaction assessment so your existing policy engine decides.

Scan a message

POST /v1/scans · POST /v1/integrations/scan

Request — text or combined inputs, optional Tier 1 language (en, pcm, yo, ha, ig).

{ "text": "Please send your OTP to 0912 345 6789 now", "language": "en" }

Response — a typed ScanResult plus a shield context block:

{
  "scan_id": "…",
  "verdict": "likely_scam",
  "risk_score": 45,
  "scam_types": ["bank_impersonation"],
  "reasons": [ { "code": "requests_secret_code", "text": "It asks you to share a private code…", "evidence": "send your OTP" } ],
  "community": { "available": true, "reports": 3 },
  "customer_message": { "language": "en", "text": "…" },
  "shield": {
    "reputation": [
      { "kind": "phone", "value": "0912 345 6789", "reports": 3, "verified": 2, "pending": 1,
        "first_seen": "2026-09-01T08:00:00.000Z", "last_seen": "2026-10-01T08:00:00.000Z" }
    ],
    "official_channels": [
      { "value": "0912 345 6789", "status": "not_found", "name": null, "shortName": null }
    ]
  }
}

Verdicts — safe · caution · likely_scam · scam. A verified report yields scam (hard evidence).

Assess a transaction

POST /v1/assess (tenant API key, Authorization: Bearer)

{ "amount": 6000000, "payeeNovel": true, "accountAgeDays": 2, "message": "Send your OTP now" }

→ { "action": "block", "risk_score": 84, "policy": "…" }

Actions: allow, warn, delay, review, block. Custom policy.bands are accepted only in development; production policy must come from trusted server configuration.

Official-channel check

POST /v1/integrations/verify-channel · directory:read

curl -X POST /v1/integrations/verify-channel -H "X-Api-Key: shd_live_…" \
  -H "Content-Type: application/json" -d '{"type":"phone","value":"0912 345 6789"}'

// 200
{
  "value": "0912 345 6789",
  "official": "not_found",
  "channel": null,
  "reputation": { "kind": "phone", "value": "0912 345 6789", "reports": 3, "verified": 2, "pending": 1 }
}

Use it in your send-money flow: if the beneficiary's phone or a link in the message is not an official channel for the named bank, surface a confirmation screen.

Reputation lookup

POST /v1/integrations/lookup · lookup:read — identifier type account | phone | url

{ "type": "phone", "value": "0912 345 6789" }

→ { "kind":"phone", "reports":3, "verified":2, "pending":1, "first_seen":…, "last_seen":… } or 404.

Only verified reports move the scan verdict. Pending reports are shown as signals, never as proof.

Report an identifier

POST /v1/reputation/reports (session) — body type, value, scamType, optional evidence.

{ "type": "phone", "value": "0912 345 6789", "scamType": "bank_impersonation", "evidence": "asked for OTP" }

→ 202 { "report_id": "…", "status": "pending", "identifier": "…" }

A moderator verifies reports. Only after verify does the identifier earn its reputation weight.

Verifiable checks

POST /v1/certificates (session) · GET /v1/certificates/:token · GET /c/:token

{ "scan_id": "3f1a…" }

→ 201 { "certificate_id": "…", "card_url": "/c/…", "verify_url": "/v1/certificates/…", "verified_until": "…" }

The verdict, score, categories and redacted message are taken from the server-side scan record for scan_id — never from the request — so a card can never claim a scam message is safe. You can only seal a scan you ran while signed in, and scans expire after 48 hours. The card renders at /c/:token; verifying the token (GET /v1/certificates/:token or /v1/integrations/certificates/:token) returns the sealed payload — tampering or expiry fail validation.

Voice verdicts

POST /v1/voice/speak — text + Tier 1 language + optional provider, returns base64 audio.

{ "text": "This is likely a scam. Do not send money or share codes.", "language": "pcm", "provider": "simulated" }

GET /v1/voice/providers — lists the configured synthesis backends.

Link preview

POST /v1/link-preview — fetch a public URL through the SSRF-safe fetcher.

{ "url": "https://secure.gtbank.com/app" }

→ { "url": "…", "status": 200, "content_type": "text/html", "bytes": 2412, "truncated": false, "title": "…", "description": "…", "signals": [] }

Never executes page scripts or loads subresources; private and loopback hosts are rejected with 422. Rate limited to 10/min per IP.

Batch scan

POST /v1/batch/scan — 1 to 25 messages in one call (anonymous or X-Api-Key with scans:write).

{ "items": [
  { "text": "Send your OTP now", "language": "en" },
  { "text": "https://bit.ly/claim your prize" }
] }

→ { "count": 2, "results": [ { "verdict": "likely_scam", "risk_score": 58, "shield": { … } }, … ] }

Media uploads

POST /v1/media/scan — raw bytes with the media type as Content-Type.

curl -X POST /v1/media/scan -H "Content-Type: image/png" --data-binary @screenshot.png

→ { "accepted": true, "kind": "image", "bytes": 24123, "analysis": { "scanned": false, "note": "…" } }

Magic bytes are sniffed to confirm the true type; SVG/executables and mismatched declared types are refused (415) and uploads are capped at 8 MiB (413). The artifact is validated, never rendered — send the message text to /v1/scans for a verdict.

Fraud-wave alerts

GET /v1/alerts/waves (session) — active and resolved waves from the last 48 hours.

When moderators verify several reports for the same identifier within 30 minutes, a wave fires (logged, webhook fraud_wave.detected, readable here). Use it to watch campaigns before the first tip-off card is issued.

Launch-readiness audit

GET /v1/ops/readiness (session) — { "status": "ready|degraded", "checks": […], "recommendations": […] }

One probe across persistence, rate limiting, auth, speech, certificates, blind-index pepper, and TLS posture before you point a bank at the service.

Webhooks

POST/GET /v1/webhooks · DELETE /v1/webhooks/:id (tenant API key)

Events: scan.completed, assess.completed, fraud_wave.detected. Delivery signatures verify with the webhook secret. Webhook delivery currently runs in-process; durable retries are not yet available.

Billing usage API

GET /v1/billing/plans returns published metered rates. Use a tenant bearer key with billing:read at GET /v1/billing/usage for a trailing 30-day estimate. Estimates are not invoices; checkout and payment collection are not implemented.

Bank integration flow

  1. Onboard — sign in, mint an integration key with scans:write + directory:read.
  2. At transfer time — call /v1/integrations/scan with the message the customer pastes; show the shield verdict inline.
  3. At beneficiary entry — call /v1/integrations/verify-channel when the customer claims a phone or link came from their bank.
  4. Policy — fold risk_score and verdict into /v1/assess for delayed/review/block actions.
  5. Incident loop — your customers can report identifiers; verified reports improve everyone's future scans.

Managing API keys

POST /v1/integration/keys · GET /v1/integration/keys · DELETE /v1/integration/keys/:id (session)

{ "name": "core-banking-transfer-gate", "scopes": ["scans:write", "directory:read"] }

The raw key is returned once. Revoke keys per environment (test, prod), never share them, and rotate on personnel changes.

Errors, limits and policies

StatusMeaning
400Invalid or unverifiable input (also certificate tamper/expiry).
401Missing or invalid credentials.
403Key lacks the required scope.
404Route, report, or reputation not found.
409Conflict (duplicate account, non-pending report).
429Rate limited — retry after the stated seconds.
413 / 415Payload too large / wrong content type.
503Optional dependency unavailable (no persistence, provider, or keyring).

Limits — consumer scans: 20/min per IP · integration scans: 40/min per key · reports: 3/hour per IP · request bodies ≤ 64 KiB.

Privacy — message text is redacted before analysis and never stored in full. Identifiers are blind-indexed; the production template encrypts them at rest. Ship Strict-Transport-Security and the documented CSP on any public deployment.

Languages — result wording ships in English, Nigerian Pidgin, Yorùbá, Hausa, and Igbo. language_reviewed flags copy not yet reviewed by native speakers.
